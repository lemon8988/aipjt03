# 요구사항 정의서

**약속 장소 플래너** — 참여자 2~4명의 위치와 날짜·시작 시각을 받아, 이동 부담이 작은 만남 지점(지하철역)과 그 주변 장소를 추천하고 계획으로 저장하는 Agent 서비스.
최초 기획: [약속 장소 플래너 — 요구사항·Tool·Agent 설계서](../약속%20장소%20플래너%20—%20요구사항·Tool·Agent%20설계서.md) · 이 문서는 **구현·검증 결과를 반영한 최종본**이다 (변경 내역은 4.5 설계 변경).

## 1. 선택한 도메인과 조건 충족 근거

### 1.1 도메인 선택 조건

| 조건 | 충족 근거 |
|---|---|
| Tool 로 래핑할 외부 API 3종 이상 (서로 다른 정보) | **카카오 로컬**(위치·후보 역·주변 장소), **카카오맵 대중교통 경로 조회**(이동시간·환승), **Open-Meteo**(약속 날짜 강수확률·기온). 세 API 모두 키 발급(Open-Meteo 는 불필요)과 실제 호출을 확인했다 (4.1) |
| 판단이 필요한 요청 | 이동시간·편차·날씨를 사용자의 제약(최대 이동시간, 편차 상한, 약속 날짜)과 비교해야 답할 수 있다 |
| 재계획이 의미 있는 요청 | 제약을 충족하는 후보 역이 하나도 없을 때 검색 반경·후보 수를 넓혀 다시 탐색한다 (실제 재현: 4.4) |
| 저장하고 관리할 결과물 | **약속 계획**(날짜, 시작·종료 시각, 참여자, 목적, 만남 역, 선택 장소, 생성 일시)을 저장·조회·수정·삭제한다 |
| 위험 도메인 여부 | **아니다.** 건강·금융처럼 판단이 위험하지 않으므로 전문가 조언 대체 금지 안내는 두지 않는다 (F3011 해당 없음) |

### 1.2 외부 API 와 이용 조건 (NF3007)

| API | 제공 정보 | 사용 Tool | 이용 조건 |
|---|---|---|---|
| 카카오 로컬 | 키워드·카테고리 장소 검색 (지하철역, 음식점, 카페, 문화시설, 관광명소) | `geo_loc`, `find_stn`, `find_spot` | 카카오 디벨로퍼스 REST API 키. 호출 한도는 앱 설정 기준 **전체 API 3,000,000건**(사용자 확인). **응답 저장 금지** → 실시간 호출만 하고, 계획에는 사용자가 확정한 이름·시각만 저장(좌표·주소·URL 미저장), 로그에는 호출 인자·건수·소요 시간만 남김 |
| 카카오맵 대중교통 경로 조회 | 출발·도착 좌표 간 경로, 소요시간(초), 환승 수 | `get_route` | 같은 REST API 키, 앱에서 카카오맵 API 활성화 필요. 출발 시각을 지정할 수 없어 **조회 시점 기준**. 응답 저장 금지(문의글 기준이며 공식 답변은 확인하지 못함) → 보수적으로 해석해 저장하지 않음. 앱은 **1개만** 사용(무료 쿼터가 처음 활성화한 앱 기준) |
| Open-Meteo | 날짜별 강수확률·최고/최저 기온 | `get_wx` | 키 불필요, **비상업 무료, CC BY 4.0** → 응답 `meta.notes` 에 출처 표기. 예보는 오늘+14일까지만 사용 |
| LLM (GPT `gpt-4o-mini`, OpenAI 호환) | 요청 분석, 응답 문장, 이상 실행 원인 진단 | - | GMS 또는 OpenAI 키(`LLM_API_KEY`, 환경변수). 모델 호출은 3곳뿐이며 규칙으로 판단할 수 있는 단계에서는 호출하지 않는다 |

### 1.3 대표 요청: 제약, Tool 순서, LLM 만으로 답하면 틀리는 점

요청의 조건은 **기준**(날짜·시작 시각) / **선호**(위치, 목적, 우선순위) / **제약**(최대 이동시간 90분·편차 30분 기본, 사용자가 말하면 그 값)으로 나눈다.

| # | 요청 (실제 사용) | Tool 순서 | 기대 결과 | Tool 없이 LLM 만으로 답하면 틀리는 점 |
|---|---|---|---|---|
| S1 | "잠실이랑 건대 사는 둘이 토요일 오후 2시에 데이트, 할 거 많은 곳으로" | geo_loc → get_wx → find_stn → get_route → find_spot | 재계획 없이 충족, 추천 3곳 | 실제 이동시간과 후보 역 주변 장소 수를 알 수 없어 근거를 지어낸다 |
| S2 | "중앙이랑 건대 사는 둘이 토요일 오후 2시에 만날래, 이동 적게" | 위와 동일 (위치 모호 되묻기 포함) | 반경 3000m 에 역이 없어 5000m 로 **재계획 1회** 후 충족 | '중앙' 이 어느 도시인지, 그 중간 지점에 역이 있는지 알 수 없다 |
| S3 | "수원이랑 춘천 사는 둘이 토요일 오후 2시에 만나고 싶어, 이동 적게" | 위와 동일 | 재계획 **3회 상한** 도달, 사유와 함께 조건 완화를 되묻기 | 두 지역 사이 후보 중 90분 상한을 넘는 폭(양수역 94분)을 계산할 수 없다 |
| S4 | S1 과 같은 요청 + `get_route` 일부 실패 주입 | 위와 동일 | 실패한 후보만 제외, 사유 표기 | 실패한 후보를 임의의 값으로 채워 추천할 수 있다 |
| S5 | "안녕", "사용법 알려줘" | 없음 | 계획 단계를 건너뛰고 바로 응답 | (Tool 이 필요 없는 요청) |
| S6 | "같은 조건에서 음식점 많은 쪽으로" | 이미 조회한 결과 재사용 (호출 0회) | 우선순위만 갱신, 위치·날짜 유지 | 이전 조건을 기억하지 못하면 되묻거나 틀린다 |
| S7 | "송도랑 마석에서 모일 장소 추천해줘" | (되묻기) → 답변 후 전체 흐름 | 날짜·시작 시각이 없으면 **Tool 호출 전에** 되묻기 | 날짜·시각을 임의로 정한다 |
| S8 | "잠실이랑 건대 … 데이트" (우선순위 없음) | (되묻기) | 우선순위를 선택 버튼으로 되묻기 | 우선순위를 임의로 정한다 |
| S9 | S1 요청, 카카오 키 없음 | geo_loc 실패 | 재계획 없이 설정 안내 | - |
| S10 | "잠실에서 7시 전에 끝나야 해" | (되묻기) | 위치·날짜·시작 시각을 지어내지 않고 되묻기 | 시작 시각·날짜를 임의로 가정한다 |

### 1.4 저장할 결과물

| 항목 | 내용 |
|---|---|
| 저장 값 | 날짜, 시작 시각, 종료 시각(없으면 `null`), 참여자 위치명, 목적, 우선순위, 만남 역, 선택 장소, 생성·수정 일시 |
| 겹침 처리 | 같은 날짜에 시간이 겹쳐도 **저장은 막지 않고**, 겹치는 계획의 id·시각·역을 저장 결과(`conflicts`)로 알린다. 종료 시각이 없으면 시작+3시간으로 겹침만 판정한다 |
| 처리 주체 | 사용자가 이미 정한 값이므로 Tool 이 아니라 백엔드 API (`/api/plans`) |

## 2. 기능 요구사항

> 필수 기능은 명세서의 항목을 그대로 두고 표현만 도메인에 맞췄다. 증빙은 [05_검증결과.md](05_검증결과.md) 와 `docs/screenshots/` 참조.

| 번호 | 분류 | 요구사항명 | 구현 내용 | 우선순위 | 상태 |
|---|---|---|---|---|---|
| F3001 | Tool | Tool 명세 정의 및 등록 | `geo_loc`·`find_stn`·`get_route`·`find_spot`·`get_wx` 의 이름·설명·입력 스키마를 정의해 레지스트리에 등록. 외부 API 툴(5)과 로컬 서버 API 툴을 구분(`kind`)하며, 모든 Tool 은 `ok`+`data` 또는 `error(code,message)` 로 반환하고 예외를 밖으로 던지지 않음 | 필수 | 구현 |
| F3002 | Tool | 후보 조회 Tool | `find_stn`: 중심 좌표 주변 후보 지하철역 (반경 기본 3000m, 노선별 중복 합침, 반경 보정 시 `meta` 에 밝힘). `geo_loc`: 위치 이름→좌표, 모호하면 `AMBIGUOUS` | 필수 | 구현 |
| F3003 | Tool | 상세정보 조회 Tool | `get_route`: 참여자→후보 역 이동시간(분)·환승 수. 기준은 조회 시점(`meta.basis`). 경로 없음은 `NO_ROUTE` 이며 그 후보는 값을 채우지 않고 판단하지 않은 채 제외 | 필수 | 구현 |
| F3004 | Tool | 보조 정보 검색 Tool | `find_spot`: 후보 역 주변 음식점·카페·문화시설·관광명소의 이름·주소·링크·반경 내 건수. `get_wx`: 약속 날짜 강수확률. 결과 없음은 `NO_RESULT`(개수 0) | 필수 | 구현 |
| F3005 | Agent | 사용자 요청 분석 | 날짜·시작 시각(기준), 위치·목적·우선순위(선호), 이동시간·편차 상한(제약)을 추출. 뽑지 못한 값은 `null` 로 두고 되묻기 | 필수 | 구현 |
| F3006 | Agent | 작업 계획 수립 | 의도에 따라 Tool 과 호출 순서를 계획으로 구성·보관. 인사·사용법 등 Tool 이 필요 없는 요청은 계획 단계를 건너뜀 | 필수 | 구현 |
| F3007 | Agent | Tool 호출 및 결과 통합 | 앞선 결과를 다음 입력으로 전달(좌표→후보 역→경로→장소). 호출이 실패하면 사유를 기록하고 다음으로 진행(해당 후보만 제외) | 필수 | 구현 |
| F3008 | Agent | 제약 적합성 판단 | 이동시간으로 최대·편차를 계산해 제약과 비교(경계 포함), 우선순위 점수 계산. 확인할 수 없는 값은 지어내지 않고 "판정 불가", 이동시간은 조회 시점 기준임을 표기 | 필수 | 구현 |
| F3009 | Agent | 재계획 | 충족 후보 0개일 때만 반경(3000→5000→8000m)·후보 수(8→12)를 넓혀 재계획. 이미 조회한 결과 재사용, 상한 3회, 도달하면 사유(가장 근접한 후보·초과 폭)와 함께 조건 조정을 되묻기 | 필수 | 구현 |
| F3010 | Agent | 대화 맥락 유지 | 세션 메모리에 조건·직전 추천 요약·정규화된 Tool 결과 보관, 바뀐 조건만 갱신, Tool 원본 응답은 보관하지 않음 | 필수 | 구현 |
| F3011 | Agent | 최종 응답 생성 | 추천 3곳을 판단 근거(참여자별 이동시간·편차·날씨·장소 수)와 함께 제시, 제외 후보의 사유 표기. 위험 도메인이 아니므로 면책 안내는 해당 없음 | 필수 | 구현 |
| F3012 | 로깅 | 실행 이벤트 발행 | 단계 진입·종료, Tool 호출 요청·응답·소요 시간, LLM 의 의도 분류와 이유, 재계획을 세션 id 와 함께 발행. 로깅 Agent 구현에 의존하지 않음 | 필수 | 구현 |
| F3013 | 로깅 | 실행 로그 저장 | 로깅 Agent 가 이벤트를 구독해 세션 단위 JSONL 에 순서대로 저장. 수집·저장에 LLM 미사용, 응답 원문 미저장, 저장 실패해도 대화 정상 | 필수 | 구현 |
| F3014 | 로깅 | 실행 로그 조회 및 삭제 | 세션 목록, 세션 상세(실행 순서), 삭제 제공. 수정 API 없음 | 필수 | 구현 |
| F3015 | 계획 | 계획 저장 및 조회 | 계획 저장·목록·상세 조회. 같은 날짜에 시간이 겹치면 저장은 하되 겹치는 계획을 저장 결과와 함께 알림 | 필수 | 구현 |
| F3016 | 계획 | 계획 수정 및 삭제 | 날짜·시각·역·장소 수정, 삭제. 결과가 화면 목록에 바로 반영 | 필수 | 구현 |
| F3017 | 서버 | 백엔드 API 서버 구현 | FastAPI 로 대화(`/api/chat`)·계획(`/api/plans`)·로그(`/api/logs`) API 를 서로 다른 경로로 제공, 요청·응답을 Pydantic 모델로 정의 | 필수 | 구현 |
| F3018 | UI | 프론트엔드 화면 구현 | 순수 HTML/CSS/JavaScript. 대화·계획 관리·실행 로그 화면, 모두 백엔드 API 호출로 표시 | 필수 | 구현 |
| F3019 | UI | 실행 과정 및 상태 표시 | 단계·Tool 호출 이력을 순서대로, 재계획 지점을 구분 표시. 처리 중 상태, Tool 실패·API 키 누락 안내 | 필수 | 구현 |
| F3020 | 로깅 | 이상 징후 판단 | 규칙으로 반복 호출·재계획 과다·계획 외 호출을 판정, 근거 없으면 "판정 불가", 이상 실행에만 LLM 원인 진단(판정과 분리 저장) | **심화(선택)** | 구현 |
| F3021 | Agent | Planner·Worker 구조 전환 | 선택하지 않음 | 심화 | **미선택** |
| F3022 | Tool | RAG 검색 Tool | 선택하지 않음 (이 도메인에서 쓸 문서가 없음) | 심화 | **미선택** |
| F3023 | Tool | 캘린더 연동 Tool | 선택하지 않음 | 심화 | **미선택** |

## 3. 비기능 요구사항

| 번호 | 분류 | 요구사항명 | 구현 내용 | 확인 |
|---|---|---|---|---|
| NF3001 | 보안 | API 키 관리 | 키는 `.env` 환경변수(`KAKAO_REST_KEY`, `LLM_API_KEY`)로만 관리, `.env` 는 `.gitignore`. 소스·문서·로그·스크린샷에서 실제 키 값 검색 결과 0건 | 5장 4.8 |
| NF3002 | 보안 | 화면 노출 제한 | 화면에는 키 값과 오류 상세를 노출하지 않고 코드별 안내문만 표시, `/api/health` 는 설정 여부만 반환, 전역 예외 핸들러가 상세를 숨김 | 5장 4.8 |

## 4. 기획 검증 결과

### 4.1 외부 API 호출 확인

실제 키로 API 를 코드(`scripts/check_apis.py`)로 한 번씩 호출해 응답 **구조**(필드명·타입)를 확인하고 [api_shapes/](api_shapes/) 에 저장했다 (값은 약관상 저장하지 않음).

| API | 호출 | 결과 | 확인한 사항 |
|---|---|---|---|
| 카카오 로컬 키워드(SW8) | "잠실역" | HTTP 200 | 같은 역이 노선별로 여러 건(7건 → 5개 역명) → **역명으로 합쳐야 함** |
| 카카오 로컬 카테고리(SW8) | 반경 3000m | HTTP 200 | `meta.total_count`·`pageable_count`·`is_end` 존재, 거리순 정렬 가능 |
| 카카오 로컬 카테고리(FD6) | 반경 500m | HTTP 200 | `total_count`=372, `pageable_count`=**45(상한)** → 점수에는 `total_count` 를 사용 |
| 카카오 로컬 결과 없음 | 없는 검색어 | HTTP 200 | `documents: []`, `total_count: 0` → `NO_RESULT` |
| 카카오맵 대중교통 | 잠실→건대 | 첫 호출 **HTTP 400** (`origin/destination` 가정이 틀림) → `start_x, start_y, end_x, end_y` 로 재호출 HTTP 200 | `routes[].properties.totalTime`(**초**), `transfers`, `status` 존재 (4.2) |
| Open-Meteo | 잠실 좌표, 날짜 | HTTP 200 | `daily.precipitation_probability_max/temperature_2m_max/min` |
| LLM (GPT) | 단순 호출 | OpenAI 호환 경로(`gpt-4o-mini`) — GPT 전환 후 실제 호출 결과는 배포 후 갱신 | 키·접속 주소·환경변수 로딩 확인 |
| LLM Tool 선택 | "잠실이라는 장소의 좌표를 알고 싶어요" + Tool 명세 | `geo_loc(q="잠실")` 선택 | Tool 명세만 보고 올바른 Tool 선택 |

### 4.2 Tool 출력 구조 대조

| Tool 출력 필드 | 원본 응답 필드 | 변환 |
|---|---|---|
| `geo_loc.items[].{id,name,addr,x,y}` | `documents[].{id,place_name,road_address_name or address_name,x,y}` | 좌표 문자열→숫자, 노선 접미사 제거 후 역명 합침 |
| `find_stn.stations[].{id,name,x,y,dist_m}` | `documents[].{id,place_name,x,y,distance}` | 같은 역(1.5km 이내) 합침, 거리순 |
| `find_spot.{items[],total,pageable}` | `documents[].{id,place_name,place_url,distance,…}`, `meta.{total_count,pageable_count}` | `total=total_count` |
| `get_route.{min,transfers,mode,type}` | `routes[].properties.{totalTime,transfers,type}`, `status` | **초→분**, 경로 여러 개면 최단, 상태값→실패 코드 |
| `get_wx.{rain_pct,tmax,tmin}` | `daily.precipitation_probability_max[0]`, `temperature_2m_max/min[0]` | 값이 `null` 이면 `NO_RESULT` |

**제약 판단에 필요한 속성이 응답에 있는가**: 이동시간(`totalTime`)·환승(`transfers`) ✔, 반경 내 장소 수(`total_count`) ✔, 강수확률 ✔. 실제 상영·운행 시각은 확인할 수 없으므로 임의로 정하지 않는다.

**값이 비어 오거나 결과가 없는 경우의 실제 응답 → 실패 코드** (실측)

| 실제 응답 | 실패 코드 |
|---|---|
| 카카오 로컬 `documents: []` | `NO_RESULT` |
| 대중교통 `status=NO_RESULTS` (서울→부산, 일부 아주 가까운 구간) | `NO_ROUTE` (가까운 구간은 도보 추정) |
| 대중교통 `status=STARTNODES_NULL` (바다 위 좌표) | `NO_ROUTE` |
| 대중교통 `status=EQUAL_POINTS` (출발지=도착지) | 성공, 0분 |
| Open-Meteo 강수확률 `null` | `NO_RESULT` |
| 카카오 HTTP 401·403 / 429 / 400 | `NO_KEY` / `RATE_LIMIT` / `BAD_INPUT` |

### 4.4 설계 시험: 재계획 조건과 상한

## 5. 제외·한계

- 심화 F3021~F3023 은 선택하지 않았다.
- 이동시간은 조회 시점 기준이라 약속 시각의 실제 운행과 다를 수 있다. 출발 시각을 지정할 수 없다.
- "음식점 많게/할 거 많게"는 평점이 아니라 반경 500m 안의 **검색 건수** 기준이다.
- 요청 분석의 우선순위는 모델이 해석할 수 있다 (예: "이동은 60분 넘지 않게" → 이동 부담 적게로 해석, 5장 4.2 `analysis_outputs.md`).
- 대화 맥락(Memory)은 서버 프로세스 메모리라 재시작하면 사라진다.
- 막차 안내는 명세서의 필수·심화 항목이 아니므로 범위에 넣지 않았다.
